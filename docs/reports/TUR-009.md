## How it works

```text
USB stick (ISO 9660 + GPT + EFI system partition; Fedora's shim and GRUB, unchanged)
  boot menu ─┬─ "Try or install TUR"  (default)   tur.live=1        → graphical.target
             └─ "Install TUR (text mode)"  [t]    tur.installer=1   → tur-installer.target

graphical.target (root = the TUR image's SquashFS + a layer in memory)
  Plasma Login Manager ── autologin ──▶ liveuser ── Plasma ── autostart ──▶ tur-installer-wizard
                                                                              │ Qt Quick on Tur.Kit,
                                                                              │ runs as liveuser
                       pkexec (polkit action org.tur.installer.engine:        │ JSON lines out,
                       liveuser only, on the medium only)                     ▼ "cancel" in
                                                                     tur-install-engine (root)
tur-installer.target                                                          │
  tur-install (root, first console) ──────── sources ───────▶ engine.sh ◀─────┘
                                                                │ checks, disks, phrase,
                                                                │ looks again, then:
                                                                ▼
              bootc install to-disk --source-imgref oci:<medium>/payload:payload \
                  --target-imgref <name> --generic-image --wipe --filesystem ext4 <disk>
                                                                │
                                   log → /var/log/tur-installer/<session>/ on the installed disk
```

### The live session

What upstream does, read for this task (ADR-0025 has the sources): Fedora's
live media use `livesys-scripts`, a GPL-3.0 shell package whose repository is
now a read-only snapshot; KDE neon's live images write `[Autologin]
User=… Session=plasma.desktop` to `/etc/plasmalogin.conf.d/`; Plasma's
first-run wizard does not start when the kernel was given `rd.live.image`;
Plasma's Welcome Center is opened by a KDED module when
`plasma-welcomerc [General] LastSeenVersion` is empty. TUR does the four
things it needs itself, all in the installer environment only:

| What | How |
|---|---|
| The root | Unchanged from ADR-0018: dracut's `dmsquash-live` mounts `LiveOS/squashfs.img` with a copy-on-write layer in memory. Nothing is kept |
| The user | `useradd liveuser` and `passwd --delete` when the environment is built; its home from `usr/lib/tur-installer/live-home/`: no screen lock, no wallet, no automatic suspend, Plasma's Welcome Center told this version was seen, autostart entries of welcome and Discover hidden |
| Sign-in | `/etc/plasmalogin.conf.d/50-tur-live.conf`: `[Autologin] User=liveuser`, `Session=plasma.desktop` |
| The installer | `/etc/xdg/autostart/org.tur.Installer.desktop` opens it with the session; an icon on the desktop and an entry in the launcher open it again |
| Not on the medium | `sshd`, Avahi, CUPS, any serial-port login (masked); the boot-health units are inert (they need `/run/ostree-booted`) |

The default target of the environment is `graphical.target`; the text entry
adds `systemd.unit=tur-installer.target`. The network can be used in the
live session (NetworkManager is no longer masked); neither installer uses one.

### The graphical installer

`desktop/apps/tur-installer`: a `QGuiApplication` with one QML module,
`Tur.Installer`, on `Tur.Kit`, started with `--standalone` (Basic style,
TUR's dark variant, nothing from KDE drawn by it). It links Qt Core, Gui,
Qml, Quick, Quick Controls 2 and D-Bus (LGPL-3.0) and the kit; its only stock
control is Qt Quick Controls' `ComboBox`, for the keyboard layout. The
screens of desktop-experience.md 11.5, with the diagnostics drawer on every
one:

| Screen | What it does |
|---|---|
| Welcome | What will happen; the language (English only, said so); the keyboard layout, from xkeyboard-config's list, applied to the live session by writing `kxkbrc` and sending KConfig's change signal, which KWin follows; "Try TUR first" closes the window |
| This computer | `tur-install-engine check`: every file of the image on the medium against its SHA-256, with progress; UEFI, processor, memory, Secure Boot; a blocking check is a two-layer message with its code, and Continue stays unavailable |
| Where to install | `tur-install-engine disks`: each disk with model (or the end of its serial number), size, connection, the end of its serial number, a picture of its partitions, what is on it in words (Windows, BitLocker, NTFS, Linux, empty) and each partition; the medium and unusable disks shown, not choosable, skipped by Tab; "Erase this disk and install TUR" and, unavailable, "Use the free space beside Windows — coming later" |
| Your account | Nothing is asked: the design creates the account at the first start (6.2). The screen says what will be asked then |
| Confirm | Red frame, no default button, the field has the keyboard: the disk by model, capacity, connection, whole serial number (with the privacy note) and stable path; on it now; after installing; what is destroyed; the Windows/BitLocker warning; the phrase. The button is enabled only by the exact phrase; pasting (Ctrl+V, Shift+Insert, middle button) is refused; Enter does nothing |
| Installing | `tur-install-engine install …`: the engine's stages, read from bootc's own lines (revalidate, prepare, copy, bootloader, finish, check, record), the time each took, during the copy the bytes written to the disk (from `/sys/block/<disk>/stat`) and the compressed size bootc reports; Cancel while the engine has written nothing, then "Cancel is not available while the disk is being written" with a "Why?" |
| Done | Success: remove the medium, Restart now / Shut down / Save the installation log. Failure: the code, what happened, the state the disk is in (untouched, erased, unknown), Save the log to a USB stick (`tur-install-engine sticks`, `save-log`), and "Back to the disks" when nothing was written |

### Privilege

The wizard runs as the live user. Every step that looks at or writes to a
disk is one run of `pkexec /usr/libexec/tur-installer/tur-install-engine
STEP`. The polkit action `org.tur.installer.engine` has `exec.path` set to
exactly that program and needs an administrator by default; a rule on the
medium allows it to `liveuser` without a password. Chosen over a privileged
D-Bus service (a resident root daemon and a frozen interface for five calls)
and over a root GUI (excluded by the task). The engine trusts nothing from
the wizard: it checks the image again, looks at the disk again (stable path,
serial number, WWN, size, fingerprint of its partitions and filesystems, not
the medium, not in use), and compares the typed phrase with the phrase it
derives itself. If the wizard goes away during an installation, the engine
carries on to its end (it ignores SIGPIPE and SIGHUP; the wizard leaves the
process running when it is destroyed), and the window refuses to close while
it writes.

### One installation path

`engine.sh` is the text installer's code, moved: payload verification, the
checks, the disk scan and its words, the phrase, the revalidation, the one
`bootc install to-disk` command with the same arguments, the check of the
partitions afterwards. The text installer sources it and keeps its screens;
`tur-install-engine` sources it and speaks JSON. Additions both get: a
systemd inhibitor while the disk is written (best effort), the root
filesystem's features recorded, and the log kept on the installed disk.

### How the graphical installer is driven in a VM

QMP `send-key` only: Tab to move, Space to press, letters to type, as a
person with a keyboard. The installer writes which control has the keyboard
to its state lines (`TUR-WIZARD: focus item=<name>`); a service of the live
session copies them to the serial port, opening the port for each line. The
driver (`tests/iso/live.py`) presses Tab until the control it wants has the
keyboard, then Space. It never clicks and never sends anything to the
guest over the serial port. AT-SPI was not used: it would need an agent
inside the guest, as the live user, talking to the host, which is a second
channel into the installer that a person does not have. The kit's accessible
names are tested in the desktop workflow instead (the walks below).

## Case-insensitive folders for Windows applications (issue 81)

**Not set on TUR's root, and it cannot be with the current disk layout.**

- bootc 1.17.1 makes the root with `mkfs.ext4 … -O verity` and has no option
  for more features (its install output, and `install.rs`); Fedora 45's
  `mke2fs.conf` does not enable casefold.
- `tune2fs -O casefold -E encoding=utf8` on the unmounted root after the
  installation is accepted (e2fsprogs 1.47.0 on the runner), and
  `dumpe2fs -h` then lists `casefold`.
- **The disk then no longer starts.** The root holds `/boot`, which GRUB
  reads at every start; Fedora 45's GRUB 2.12 does not list casefold
  (0x20000) among the ext4 features it supports or ignores
  (`grub-core/fs/ext2.c`, branch `fedora-45`) and so does not recognise the
  filesystem. Measured in run 43369283112, and again in 43381059054: the serial port shows
  `error: ../../grub-core/commands/search.c:grub_search_fs_uuid:527:no such
  device: <the root's UUID>`, then `grub>`; no rendered screen in 240 s.
  The picture is above.
- The installed root's features are recorded on every installation
  (`TUR-INSTALLER: root-filesystem … features=…`, and the iso report reads
  them from the disk): `has_journal, ext_attr, resize_inode, dir_index,
  orphan_file, filetype, extent, 64bit, flex_bg, metadata_csum_seed,
  sparse_super, large_file, huge_file, dir_nlink, extra_isize,
  metadata_csum, verity`.
- The way to issue 81 is a filesystem for `/var/home` (or a separate
  `/boot`) that GRUB need not read: a disk-layout change, with its own ADR
  and the boot and rollback proofs again (ADR-0025, options). Until then the
  Windows runtime's `--casefold` has nothing to work on, on an installed
  TUR. No check was added to the boot test: there is nothing to check yet.

The live session and the graphical installer add a few megabytes (the
program, two libraries, QML modules, configuration); the growth since
TUR-007 is the image's own (main gained programs). **The image is still on
the medium twice.** Storing it once (a read-only container store inside the

needs the overlay storage driver proven on the medium's overlay root; it was
not attempted in this change. The medium still needs an 8 GB stick.

## Decisions the owner may want to reverse

1. **The live user has no password**, may run the installation engine
   without one (polkit, on the medium only), and can sign in on the virtual
   consoles (Ctrl+Alt+F2…) without one. Remote and serial logins are off.
2. **The account is made at the first start, not in the installer**
   (design 6.2). Today that first start is the base image's first-run setup
   (`plasma-setup`), until `tur-setup` (D-06) exists.
3. **The live session may use a network** (NetworkManager is no longer
   masked on the medium); neither installer uses one.
4. **The typed phrase is required for every disk**, blank or not, as in the
   text installer and design 11.5. The task asked for it at least for disks
   that hold data.
5. **The installer opens by itself** when the live session starts, over the
   desktop; "Try TUR first" closes it.
6. **The installer runs with its standalone look** (Basic style, TUR's dark
   variant, Inter or the fallback font), not the desktop's, so that it is the
   same program the tests photograph. Light is shown in the pictures, not
   offered on the medium.
7. **Language: English only**, said so on the first screen.
8. **The graphical installer's privileged half is a shell script**
   (`tur-install-engine` over `engine.sh`), not `tur-installer-core`. The
   core library remains the design's end state (installer.md, section 0).

## What is not proven

- Everything on real hardware: firmware, disks (NVMe, SATA, USB), a USB
  stick, real graphics (the VM renders in software), HiDPI, touch.
- The live desktop beyond what the installer needs: Wi-Fi, sound, printing,
  suspend.
- Saving the log to a USB stick: the engine's `sticks` and `save-log` steps
  and their screen are tested on recorded answers only.
- A failed `bootc install` and a refusal at revalidation in a VM (the
  screens are tested on recorded answers).
- Cancelling in a VM: the window in which it is offered is a few seconds
  long (the engine checks the image again, then the disk).
- A keyboard layout other than US in a VM (the layout is applied through
  KConfig's signal; KWin's reaction was read in its source, not seen).
- A screen reader. The accessibility walk reads Qt's accessibility
  interfaces, not AT-SPI.
- Memory: the live runs had 6 GiB; the minimum for the live session was not
  measured. bootc took longer under the live session (92 to 316 s, against
  about 120 s from the text installer in the same runs).
- The recorded engine answers were written by hand in the engine's format
  (the engine logs every line it sends; comparing them with a real run is a
  follow-up).

## Findings

1. **The pinned base image disappeared from quay.io** during this work
   (`manifest unknown` for the digest of 12 November); pull request 88
   re-pinned it. Every image build fails until a pin is renewed when this
   happens again.
