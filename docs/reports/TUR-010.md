## The engine stage

`image/engine/llama-cpp.sh`, in a stage `FROM` the pinned base:

1. `fetch` (network): `dnf install gcc gcc-c++ cmake ninja-build glslc
   vulkan-headers vulkan-loader-devel spirv-headers-devel` from the base's
   own repositories (90 MiB downloaded; gcc 16.2.1-3.fc45, the same
   release as the base's libstdc++; cmake 4.3.0; glslc 2026.2), then the
   source archive, checked against the SHA-256 in `llama-cpp.lock`.
2. `build` (no network): CMake with `GGML_NATIVE=OFF`,
   `GGML_BACKEND_DL=ON`, `GGML_CPU_ALL_VARIANTS=ON`,
   `GGML_BACKEND_DIR=/usr/libexec/tur/llama.cpp`, `GGML_VULKAN=ON`,
   OpenMP, no web interface, no OpenSSL, `-ffile-prefix-map`, RPATH
   `$ORIGIN`; target `llama-server` only; stripped.

What it gives: `llama-server` (`version: 9840 (8c146a8) built with GNU
16.2.1 for Linux x86_64`), `libllama`, `libggml`, `libggml-base`,
`libmtmd` and 15 backends: `cpu-x64`, `sse42`, `sandybridge`, `ivybridge`,
`piledriver`, `haswell`, `skylakex`, `cannonlake`, `cascadelake`,
`icelake`, `cooperlake`, `zen4`, `alderlake`, `sapphirerapids`, and
`vulkan`. It takes from the image only `libc`, `libm`, `libgcc_s`,
`libstdc++`, `libgomp` and `libvulkan`. The final stage runs `--version`
and `--list-devices`. Licences: llama.cpp (MIT), nlohmann/json (MIT, with
Abseil lines under Apache-2.0, whose text TUR adds), cpp-httplib (MIT),
stb_image, miniaudio, subprocess.h and llamafile's sgemm, copied out of the
source by the script, which fails if one is empty. SBOM:
`MIT AND Apache-2.0 AND (MIT OR Unlicense) AND (MIT-0 OR Unlicense) AND
Unlicense`, held against the allow-list.

`tur-ai-local` looked for the backends beside `/usr/bin/llama-server`;
it now follows the link first (`engine::backends`), so `hardware`,
`models` and `recommend` count the processor variants and Vulkan.

## Deviations and decisions

1. **P@x's units are installed and the catch-up timer is enabled for
   every user**, which #85 did not list: pax-service.md section 6 says so,
   and the desktop programs of #59 need `org.tur.Agent1` to be
   activatable. With P@x off the timer runs `tur-pax schedule wake` once
   after sign-in, which reads the settings and ends. `systemctl` reports
   the timer's unit file state as "disabled" because the link is under
   `/usr/lib`, not `/etc`; it is active and ran.
2. **The boot-test image adds `dbus-daemon` and `gnome-keyring`** from the
   base's repositories, for `tests/pax/service_e2e.py` (its private bus;
   its Secret Service). The product image has neither; its session bus is
   dbus-broker and its password store KWallet.
3. **The boot test's guest has 10 GiB, not 4**: `tur-ai-local` serves a
   model only when its need and a 1 GiB reserve fit in the memory free at
   that moment (Qwen3 0.6B: 2.15 GB; Qwen3 4B: 6.15 GB). With 8 GiB the
   guest had 7.05 GB free and Qwen3 4B was refused with TUR-AI-LOCAL-006
   (boot run 43487318802), correctly. **Each local model's check follows
   the verdict `tur-ai-local check` gives on the machine before anything
   is done**: `fits` must be served and pass P@x's run; `not-now` must be
   downloaded and refused by `serve` with TUR-AI-LOCAL-006; `too-large`
   must be refused by `pull` with TUR-AI-LOCAL-005, nothing downloaded. An
   answer from at least one model is required only where the guest is
   sized for it (`report.py --require-local-answer`, the boot workflow).
   The installer medium's proof guest (4 GiB, 2.8 GB free) gives both
   refusals: Qwen3 0.6B `not-now` (006 from serve), Qwen3 4B `too-large`
   (005 from pull, nothing downloaded); iso run 43505484566 checks them
   and passes, and the answer check is informational there.
4. **The tool-result budget is per result**, a quarter of the context
   (one byte per token): 8 192 bytes for the local preset. A long task can
   still outgrow the context. The first version used an eighth (4 096
   bytes); `tur-ai-local recommend` alone prints about 10 KB on the guest,
   and was cut at 8 192 bytes in the head's boot run.
5. **local-ai's Fedora container re-pinned**: `quay.io/fedora/fedora:45`
   at `sha256:fa773d10…` (read 2026-11-12) answered "manifest unknown" on
   2026-11-13 and failed the `fedora` and `compare` jobs; it is now
   `sha256:e15959f3…`. That image has no mirror, so this will recur. The
   desktop builder (`desktop/ci/builder.lock`) pins the same vanished
   digest; it still passes because its image comes from the Actions
   cache, and a rebuild of the builder would fail.
6. **Reproducibility of the engine across days**: the compilers come from
   the base's repositories as they are on the day; two builds of one
   workflow agree (checked), a build on another day may not.

## Limits

- One run per model on the head; what a small model does varies. Qwen3
  0.6B made no tool call in any run on the guest and gave one wrong
  answer; Qwen3 4B made one tool call in its one task.
- Nothing ran on a graphics processor or on real hardware, and no speed
  here says anything about a PC.
- The Vulkan backend never ran a model: CI has no graphics processor.
- `ai_local_status` still cannot see a running model from P@x's sandbox
  (`TUR-AI-LOCAL-027`; needs `org.tur.AiLocal1`).
- The supervisor's `/metrics` probe cancels a task every ~12 s in the
  engine log during a long prompt (#74, known).
- tur-apps was run for listing, sources and an offline plan only;
  nothing was installed on the image (Flathub is off for a new user, and
  `tur-apps plan` says so with TUR-DESKTOP-APPS-008).
