## Decisions

**Fetch, not vendor.** One build step, `programs.sh fetch`, has network and
runs `cargo fetch --locked` per component; it compiles nothing. Each
`Cargo.lock` pins every crate by version and SHA-256, Cargo checks every
download against it, and `--locked` refuses a lockfile that would change.
The compile step has no network. Vendoring would have put about a hundred
crates' sources (Windows-only ones included) into the repository, to be
regenerated by CI on every dependency change since nobody runs Cargo locally;
what it would add is independence from crates.io at build time, which the
build does not have anyway (two pinned images are pulled). Reasoning in
`image/README.md`. Reproducibility held: identical image IDs in every image
run, the second build each time without cache.

**The release profile is set in the build stage**, by
`CARGO_PROFILE_RELEASE_*` in the `Containerfile`, for every program alike
(one code-generation unit, no incremental, no debug information, stripped).
No component's `Cargo.toml` was changed.

**Placement.** `/usr/bin`: what a person types or an adapter starts by path.
`/usr/libexec/tur`: `tur-boot-health` (units start it; linked from
`/usr/bin`), `tur-pax-providers` (a configuration check that `tur-pax`'s
library already contains) and `tur-installer` (dry-run tools of the
installer core). Reverse any of these by changing one line of
`image/programs.tsv`.

**Licences.** `programs.sh` asks Cargo which crates each program links,
copies the licence files each crate ships and writes `crates.tsv`.
`scripts/sbom-programs.py` puts the programs and crates in the SBOM (1,751
RPM packages plus 11 programs and 70 crate entries) and fails the image
workflow on a crate whose licence is not on a permissive allow-list: TUR
programs link their crates statically, so a GPL or LGPL crate must not slip
in (licence review item 13, now done). All 69 crates pass: MIT, Apache-2.0,
BSD-3-Clause, ISC, Unicode-3.0, CDLA-Permissive-2.0, mostly as
"MIT OR Apache-2.0". `zstd-sys` carries zstd, dual BSD-3-Clause/GPL-2.0-only,
taken as BSD-3-Clause. Of the Rust toolchain's two notice files the image
takes `COPYRIGHT-library.html` (1.5 MB, the standard library), not
`COPYRIGHT.html` (14.4 MB, the whole toolchain); the first run shipped both.

**Build manifest, schema version 2**: `programs` (name, version, path,
SHA-256, size, component, tool directory with the hashes of its two files),
`catalogue`, `third_party_crates`, `image.size_bytes`.
`validate-manifest.py` also holds the programs against `image/programs.tsv`.

**Glibc note still holds.** Every program runs `--version` inside the final
image during the build. `ldd` in the smoke test: each needs only
`libc.so.6`, `libgcc_s.so.1` and the loader; `tur-pax` and `tur-pax-memory`
also `libm.so.6`. The C code of `zstd-sys` and `ring` is linked statically.

**Runtime needs.** Present in the base, nothing added: `bwrap` (bubblewrap
0.13.1, not set-user-ID), `prlimit` (util-linux 2.42.4), `lsblk`, `udevadm`,
`journalctl`, `fwupdmgr`, `systemctl`, `tar`, `bootc`, and every command
`tur-diag` collects with (`lspci`, `lsusb`, `vulkaninfo`, `wpctl`, `nmcli`,
`bluetoothctl`, `blkid`, `dmesg`, …). The smoke test checks each. No package
was added to the image.

## Desktop programs: not in the image

`tur-centre` (and `tur-settings`, merged to main during this work) are left
out. What stands in the way, in order:

1. **`desktop/` has no install rules.** `desktop-kit.md` says so ("No install
   rules. Nothing is installed into the image"). Installing means adding
   `install()` rules, a launcher entry (`.desktop` file) and its icon under
   `desktop/`, which this task may not touch (another agent owns it).
2. **"The same Qt as the image" cannot be held reproducibly with today's
   tools.** The build stage would start from the image's own base
   (`fedora-kinoite@digest`) and `dnf install` `cmake`, `gcc-c++`,
   `qt6-qtbase-devel`, `qt6-qtdeclarative-devel` and friends there, then copy
   only the installed files out, so the final image gains no build package.
   But Fedora's repositories hold only the newest build of a package: the
   pinned base has `qt6-qtbase-6.11.2-3.fc45`, and the day Fedora ships
   6.11.3 the `-devel` package no longer matches it, and pinning
   `qt6-qtbase-devel-6.11.2-3.fc45` stops resolving. A build from a given
   commit would then not repeat. Holding it needs either a mirror of the
   matching `-devel` RPMs (Koji keeps them) pinned by checksum, or a check
   that fails the build when the `-devel` EVR differs from the base's
   `qt6-qtbase`; the second is cheap and should come with item 1.
3. **The kit's face, Inter, is not in the image** (`rsms-inter-fonts` is in
   the desktop builder, not in Kinoite). Without it fontconfig substitutes
   and the program would not look as its reference images; adding the
   package (OFL-1.1, Fedora) belongs with item 1.

Nothing of the desktop was half-installed.

## Findings

1. **SELinux, test harness only**: `avc: denied { append } … comm="dbus-broker"
   path="/var/lib/tur-boot-test/report/second-boot/components-session.txt"
   scontext=system_u:system_r:system_dbusd_t tcontext=system_u:object_r:var_lib_t
   tclass=file`. `systemd-run --machine=user@.host --user` passes its own
   standard error through the system bus to the user's manager; the bus
   daemon may not write a file under `/var/lib`, the connection drops, and
   the test fell back to a PAM session. Fixed in the test (nothing but
   `/dev/null` given to that command). Not a product issue.
2. **P@x refuses a folder written the usual way.** On this system `/home` is a
   link to `var/home` (Fedora Atomic). `tur-pax run --grant-read
   /home/turtest/Documents` exits 1: `TUR-AI-SANDBOX-002: … it is reached
   through a link and resolves to "/var/home/turtest/Documents"`. The same
   folder as `/var/home/turtest/Documents` is accepted. `GrantRules::admit`
   (`services/tur-pax/src/sandbox.rs`) compares `canonicalize(path)` with the
   path as written. Proposed change (not made: `services/tur-pax` belongs to
   another agent): resolve the home directory's own link before comparing,
   or accept a path whose only link is a whole leading system link such as
   `/home → var/home`; links below the home directory stay refused.
   Informational check in the boot report.
3. **SELinux, product: `tur-diag` → `bootc` under no-new-privileges.**
   `avc: denied { nnp_transition nosuid_transition } … comm="tur-diag"
   scontext=unconfined_u:unconfined_r:unconfined_t:s0-s0:c0.c1023
   tcontext=unconfined_u:system_r:install_t:s0-s0:c0.c1023 tclass=process2
   permissive=0`. `/usr/bin/bootc` is `install_exec_t` and enters
   `install_t`; a process with `NoNewPrivs`, as every one in P@x's sandbox
   is, may not. One denial per `diag_get_status` the assistant performs; the
   exec fails and the deployment fields are null. Reproduced outside the
   test with `setpriv --no-new-privs tur-diag status`. As an ordinary user
   `bootc status` would refuse anyway (it needs root). Not fixed: the
   remedies are a policy rule allowing `nnp_transition` into `install_t`
   (wrong: it widens bootc's entry for every caller) or `tur-diag` not
   starting `bootc` when it is not root (a change of a few lines in
   `services/tur-diagnostics/src/identity.rs`, more than the one line this
   task may make). Recommended: the second. Informational check.
4. **Inside the sandbox `tur-diag status` cannot count failed units**:
   `failed_units` is `null` in what the model receives, because the sandbox
   has no `/run` and so no service manager to ask. The shipped
   `diag_get_status` tool therefore gives the assistant the build and kernel
   but not the one figure that says something is wrong. The P@x test checks
   only that the key exists. Needs a decision in the orchestrator design
   (a status reader outside the sandbox, or a read-only socket).
5. **Three of `tur-storage`'s five declared tools have no adapter**
   (`storage_mount`, `storage_unmount`, `storage_unlock`) and are therefore
   not offered, as #43 records. The first smoke test wrongly required an
   adapter for every tool; it now prints which are offered.
6. **SELinux denials of the base, unchanged by TUR**: in every boot,
   `chcon` from `unconfined_service_t` and `tuned_t` denied `mac_admin`,
   and `bootupctl` (`bootupd_t`, permissive) reading
   `/sysroot/.bootc-aleph.json` (`default_t`): 15 to 17 per boot. TUR-003
   open item 5. Apart from findings 1 and 3, every denial in the three
   journals is one of these.
7. **The user's bundle lacks the boot-health records** (journal access).
   Expected; the bundle's README could say a support bundle should be made
   as administrator.

## What is not proven

- Nothing on real hardware; the device, storage and diagnostics results
  describe a QEMU Q35 machine.
- The programs ran in a session started by the service manager, not in a
  graphical desktop session a person logged into; no program was started from
  the desktop.
- No real model was called; the provider is the test's script.
- `tur-update` was run read-only (`status`, `check`); nothing was staged
  through it.
- The SBOM's crate entries come from Cargo's view of each lockfile, not from
  inspecting the binaries.
- The identifier probe sees the container image, not an installed system,
  and no window class.
