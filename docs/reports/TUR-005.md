## The go or no-go: step 2

**Go.** A kernel argument written as a GRUB variable in
`/usr/lib/bootc/kargs.d` survives `bootc container lint`, `bootc install` and
OSTree, and Fedora's GRUB expands it when it builds the menu. GRUB can count in
its environment block on this layout.

First shown in run 43189478889, on an image that had the fragment and the
kernel-argument file and **no TUR program at all**, and required by the boot
test in every run since:

| What | Evidence |
|---|---|
| bootupd wrote the fragment into `grub.cfg` before the menu is built | `### BEGIN 08_tur_boot_count.cfg ###` precedes `### BEGIN 10_blscfg.cfg ###`, read from the installed disk by the host and again in the guest |
| The variable survived | The loader entry on the installed disk: `options root=UUID=… rw console=tty0 console=ttyS0,115200n8 tur.boot_test=1 $tur_boot_args ostree=…` |
| Ordinary boot | `/proc/cmdline` of the first two boots: `… tur.boot_test=1 tur.boot_contract=1 ostree=…`. No `$`, no `tur.boot=`, and nothing in the block |
| Counted boot | The test set `boot_counter=2` by hand and restarted. Third boot: `… tur.boot_contract=1 tur.boot=trial tur.boot_tries_left=1 ostree=…`, and the block held `boot_counter=1` |
| Read from outside | The host read the same three kinds of boot from the kernel command lines on the serial console: `none, none, trial/1` |

The contingency of design section 5.4 is not needed.

## What was built

**The GRUB half** is the fragment of design section 5.3, unchanged, in
`image/third-party-licensed/grub/` under BSD-3-Clause with greenboot's
copyright notice, and one kernel argument, `$tur_boot_args`.

**`tur-boot-health`** is one Rust program with the subcommands of the design:
`classify`, `gate`, `mark-good`, `record-failure`, `arm`, `export-evidence`,
`status`, `acknowledge`. Everything that touches the machine goes through one
trait. The unit tests replace it with a machine in memory that runs the
fragment's logic, finalises a staged deployment as OSTree does, and can lose
power before any write. The program has no dependency outside this repository
and the Rust standard library: it carries a small JSON reader and a reader
for the subset of TOML its configuration uses.

**Units** are those of design section 6.1. The two that restart a failed trial
boot contain no TUR code: `systemctl reboot` under
`ConditionKernelCommandLine=|tur.boot=trial`.

**The gate** implements R1 to R8 with the design's limits, additional checks
from `checks.d`, and four of the twelve non-blocking checks (W1 failed units,
W8 finalisation, W10 counting usable, W12 watchdog). It records stages
BOOT-080, 110, 120, 130, 140 and 150 in the journal as it observes them.

**Not built:** `tur-boot-notify` (the notice exists as
`/var/lib/tur/boot-health/notice.json` and in `tur-boot-health status`; nothing
shows it in a session), stages BOOT-001 to BOOT-070, the other non-blocking
checks, `tur-diag` collectors. The schemas for the trial record and for
`status --json` are in `services/tur-boot-health/schemas/`, because `schemas/`
is not this task's to change.

## How the program gets into the image

A build stage in `image/Containerfile`:

```dockerfile
FROM docker.io/library/rust@sha256:f6c4a35d… AS programs   # 1.99.1-slim-trixie
COPY rust-toolchain.toml crates/ services/tur-boot-health/ …
RUN --network=none … cargo build --release --locked --offline; install …
FROM ${BASE_IMAGE}@${BASE_DIGEST}
COPY --from=programs /out/ /
```

- The toolchain is the official Rust image **pinned by digest**. The stage fails
  if its `rustc` is not the version in `rust-toolchain.toml`.
- The compile step runs **without network** and refuses a lockfile that does
  not match. That is possible because this program has no third-party crates.
  A later component that has some must vendor them or get a pinned
  `cargo fetch --locked` step; `image/README.md` says so.
- The build context is still the repository root. What is sent is listed in
  `image/Containerfile.containerignore`, which podman prefers over the root
  `.containerignore` (shown by the `image` workflow, which builds without
  naming it). A component that joins the image adds its directory there.
- **Reproducibility held** in every run of the `image` workflow since the
  stage was added. Run 43214597952: both builds produced the binary with
  SHA-256 `d0144b42…` and image ID `10bcc317…`. The compile takes 3 to 4 s;
  pulling the toolchain image is most of the roughly 20 s the stage adds to a
  build that takes three to four minutes.
- The binary links the C library of the toolchain image (Debian 13), older
  than Fedora 45's. The build runs it once in the final image so that an
  incompatibility stops the build.

Why not build in the workflow and copy the binary in: every workflow that
builds the image would have to repeat the step, `scripts/build-image.sh` would
stop being enough to build the image, and the reproducibility check would
compare two copies of one binary instead of two builds of it.

How a scenario runs: the disk the boot test leaves after its second boot is the
base of a copy-on-write overlay. The scenario's image is built `FROM` the
boot-test image with one change, copied with all others into one OCI layout
with uncompressed layers, and attached as a read-only disk. The guest runs
`bootc switch --transport oci /run/tur-test/images:<name>` and restarts. From
then on the host only reads, except where the table says it cut the power
(QEMU killed, then started again on the same disk) or pressed reset.

What a pass asserts, from inside the guest and from the console, never from
timing alone:

1. **The intended cause.** A console line or QMP event that only that failure
   produces: `Kernel panic - not syncing`, `Failed to mount sysroot.mount`,
   `Reached target emergency.target`, a QMP `WATCHDOG` event, or the gate's
   own line naming the check and its error code, read from the journal of
   each failed attempt after the rollback.
2. **The sequence of boots**, read from the kernel command line the kernel
   prints on the serial console, is exactly the expected one. A trial boot
   carries all four trial arguments; no other boot carries any.
3. **The end state**, from the surviving system's own report: which image
   runs (a marker file in each scenario image), the OSTree checksum against
   the one recorded at staging, `ostree admin status --is-default`,
   `rollbackQueued`, the gate's verdict in that boot, no `boot_counter` and
   no `tur_trial_args` in the block, no trial record.
4. **After a fallback:** one fallback event in the history with both
   versions, three attempts, the number that reached userspace and the
   reason; the failed image's digest in the rejected list; the notice with
   the design's wording; bootc's own log line; the journal entry that names
   the failed deployment; an exported journal per attempt that wrote one;
   and the attempts' journals still readable in the persistent journal.
5. **That the harness restarted nothing**, unless the scenario is a power cut
   or a person pressing reset, in which case exactly the intended actions.

## Findings: what the design got wrong or did not foresee

### 1. GRUB can act on an environment block that is out of date

This is the finding that matters most.

GRUB reads ext4 without replaying its journal. `grub2-editenv` rewrites the
block by truncating the file and writing it again, and that moves it to
another disk block (boot test, run 43189478889: physical block 4344553 before,
2163984 after; scenario X1: 2725967 before, 560677 after). The program at first
only fsynced the file after such a write. That commits the journal, but the
inode that says where the block now is has not reached its place on disk, so
GRUB still finds the old block with the old content.

Observed with the fsync alone, each time after QEMU was killed within a
fraction of a second of the write:

| Run and scenario | Written before the cut | What GRUB then did | What the block held |
|---|---|---|---|
| 43200240515 and 43207801019, `cut-fallback-step3` | `boot_counter=2` (step 3 of a fallback) | `tur.boot=fallback`: it acted on `-1` | `2` |
| 43200240515 and 43207801019, `cut-mark-good` | counter removed | `tur.boot=trial tur.boot_tries_left=1`: it counted the old `2` | no counter |
| 43200240515, `cut-finalize-*` (five cuts), and 43207801019 (six of seven) | `boot_counter=3` (arming, at shutdown) | no `tur.boot` argument: it saw no counter | `3` |

Every one of these converged on a whole, working version. The third produced a
state the classification table does not have (finding 2).

The measurement scenario X1 was added to look at this directly: rewrite the
block, sync, cut the power 0.5 s later. It used a sync of the whole filesystem
(`sync --file-system`), and GRUB acted on what had been written (runs
43207801019 and 43214598212: `boot_counter=2` written, the kernel started with
`tur.boot_tries_left=1`, the block then held `1`). A filesystem sync also
writes the metadata buffers to their place; an fsync does not.

**The program now syncs the filesystem after every write to the block.** The
design says "syncs" without saying which kind. With that change, in run
43214598212:

| Scenario | What GRUB did after the cut | The design's own prediction |
|---|---|---|
| `cut-fallback-step3` | `trial/1`, `trial/0` on the failed version, each restarted at once as rejected, then `fallback` and the rollback was finished | Row 1 of the interruption table in section 5.9: "two short extra starts" |
| `cut-mark-good` | an ordinary boot of the new version | Section 5.12: "Counter gone: ordinary boot" |
| `cut-finalize-*`, all seven | `tur.boot=trial tur.boot_tries_left=2` on the previous version, classified `stale` | Section 5.12: "Disarmed. The update was not applied" |

What is still open:

- **The window between the rewrite and the end of the sync.** A power cut
  there leaves GRUB with the old block. The states this produces are the ones
  in the first table; all converged, and the one the design did not list is
  now handled (finding 2).
- **GRUB writes where it reads.** While it sees the old block, its own
  `save_env` writes the counter into that block, which the filesystem
  already considers free. If the filesystem had given the block to another
  file before the power cut, GRUB would overwrite 1024 bytes of it. Not
  observed; I see nothing that prevents it.
- **The new version starting without a counter**, the case the design fears
  most, was not reached: OSTree makes its change of the boot order durable
  with a filesystem freeze, which also puts the counter where GRUB looks.
  That is an argument from how OSTree works, not a tested result: no cut
  landed after OSTree had changed the order.

The design names `grub2-editenv` as the way the program touches the block, so
the program still uses it. **Recommendation:** amend ADR-0014 so that the block
is written in place, 1024 bytes over the existing ones without truncating.
That closes the window and the write into a free block, and X1 is its test.

### 2. A state the classification table does not list

A power cut between arming and OSTree's finalisation leaves: no `tur.boot`
argument (finding 1), a trial record in phase `trial`, the booted deployment
is the default and is the previous one, and a counter in the block. The
design expected this boot to arrive as row 4 with `tur.boot=trial`. In run
43200240515 it was classified `unlisted` and nothing was changed, as the table
says for unknown combinations. The implementation now treats it as row 4:
the update was not applied, the counter and the record are removed, the user
is told. Six of the seven cuts of run 43207801019 ended that way. With the
filesystem sync of finding 1 the state should now arise only in a narrow
window; in run 43214598212 all seven cuts arrived as the design's row 4.

### 3. `/boot` is an automount, and requiring it stops the arming unit

`/boot` is a bind mount of `/sysroot/boot` (`ostree-system-generator`) behind
an automount with `TimeoutIdleSec=120` (`systemd-gpt-auto-generator`).
systemd stops a unit that requires a mount when it unmounts it for idleness:
a canary unit with `RequiresMountsFor=/boot` was stopped 131 s after its last
access (run 43189478889). The design's `tur-boot-arm.service` requires `/boot`
and acts in its stop action. It would have run two minutes after boot, found
nothing staged, and not existed at shutdown: **no trial would ever be armed**.

No TUR unit requires `/boot` now. They are ordered after `boot.mount` and
`boot.automount`, and the program reaches the block through the automount.
While a deployment is staged OSTree's own hold service keeps `/boot` mounted.
The boot test asserts that the arming unit is still active after the
automount has expired.

### 4. Check R1 failed in the boot that made a fallback permanent

`bootc rollback` re-points the links the kernel's `ostree=` argument goes
through. Resolved afterwards, the argument names the failed version. In run
43200240515 the gate failed R1 in every fallback boot, and because that boot
is not a trial the generic "some checks failed" notice replaced the fallback
notice. The argument is now resolved once, when the boot is classified, and a
notice about a fallback or an update that was not applied is no longer
replaced by the generic one. Both have unit tests.

### 5. A kernel image cut short is started, and the machine hangs

Design section 5.8 has GRUB start the second entry when it "cannot load or
start the kernel (missing, corrupt, rejected by Secure Boot)". With a kernel
image cut to 64 KiB (run 43200240515, `kernel-truncated`), GRUB without Secure
Boot started it. The firmware stopped in an exception handler (`X64 Exception
Type - 06 (#UD - Invalid Opcode)` on the serial console; the screen shows
`Booting 'TUR …'` and a cursor). Nothing restarts the machine from there: it
is the hang of design section 5.13, item 1, reached by a failure the design
listed as recoverable. The attempt had been counted: the harness, standing in
for a person, pressed reset after each of three hangs, and the fourth start was
the previous version (`kernel-truncated`, a manual recovery).

A kernel that GRUB refuses to load does fall back as designed. With an empty
kernel image GRUB printed `kernel is too small`, started the second entry in
the same boot with the trial arguments, and the previous version made the
fallback permanent with reason `loader` (`kernel-missing`). With Secure Boot
enforced shim may reject a damaged kernel and turn the first case into the
second. Not tested.

### 6. Smaller differences

- **bootc's rollback message has no message ID.** bootc 1.17.1 logs
  `Rolling back to image: sha256:…` with `MESSAGE_ID` unset, and the digest is
  that of the image being left, not the one returned to. The design's
  assertion on ID `26f3b1eb…` cannot be made; the scenarios assert on the
  message.
- **The watchdog reset a stopped PID 1 after 360 s, not 180 s.** QEMU's ICH9
  watchdog resets on its second expiry and the kernel driver programs the
  full timeout for that chipset version. systemd, when it freezes after a
  crash, closes the watchdog without stopping it ("watchdog did not stop!"),
  which is what lets it fire. Whether real chipsets also take twice the
  configured time is unknown.
- **The test uses the q35 machine's own chipset watchdog**, which the guest
  sees as `/dev/watchdog0`, instead of adding the `i6300esb` device the
  design names: a second watchdog would make it uncertain which one PID 1
  uses. The guest kernel has no `pvpanic-pci` driver; the ISA device is used.
- **No pstore backend is registered** in the guest (`backend: (null)`), so a
  panic in a trial leaves no pstore record in the VM.
- **The gate has no deadline for a stall before `basic.target`**: it is
  ordered after that target. systemd's own start timeouts turn most such
  stalls into emergency mode, which is covered and tested.
- **An update staged while a trial is still running** would make the
  unproven version the "previous" one of the next trial. Not handled.
- **`systemd-analyze` reports a longer startup**: about 29 s where it was
  14 s, because the gate's 15 s hold is a job of the boot. `graphical.target`
  is reached as early as before.

## The design's assumptions

Section 17 of the design document has the full table. In short:

| Assumption | Result |
|---|---|
| The argument expansion (5.4): survives bootc and OSTree; empty expansion is valid; several words become several arguments | Confirmed |
| `save_env` on ext4 on a plain partition; `increment` built in; index 1 is the previous deployment; `timeout=5` survives | Confirmed, without Secure Boot |
| `fallback=1` as a plain variable is honoured | Confirmed for a kernel GRUB refuses to load; a corrupt kernel is not refused (finding 5) |
| `bootc switch --transport oci path:reference`; layer reuse with uncompressed layers | Confirmed: 72 of 73 layers already present, 9.2 kB fetched |
| `bootc rollback` from the second entry makes the booted deployment the default | Confirmed |
| `bootc rollback` logs message ID `26f3b1eb…` | Refuted for bootc 1.17.1 |
| A unit may require `/boot` | Refuted (finding 3) |
| GRUB sees what userspace wrote to the block | Refuted after an unclean stop (finding 1) |
| The initramfs has no watchdog driver | Refuted as stated (the files are there); the driver is not active before the real root, so the effect is as assumed |
| PID 1 opens a watchdog that appears after it started | Confirmed |
| An unknown `rootflags=` option makes root unmountable | Confirmed |
| pstore works under OVMF | Refuted: no backend registered |
| Kinoite enables bootc's update timer | It does not; masked anyway |
| `bootupctl update` does not rewrite `grub.cfg` | Not contradicted; no bootloader update was pending |
| Locking finalisation at shutdown stops OSTree's stop action (5.5) | Untested |
| Disk space after an interrupted staging is reclaimed | Untested |
| A Secure Boot OVMF build is on the runner | The files are there; scenario SB not run |

## What is not proven

- **Anything on real hardware.** Real firmware and its boot-order handling,
  real drives and their write caches, real hardware watchdogs, real GPUs.
  Recorded as NOT RUN until a hardware runner exists (ADR-0002).
- **A real power cut.** QEMU was killed. The disk was a qcow2 overlay opened
  with `cache=writeback`: what the guest had flushed survives, what it had
  only written may not. That is closer to a power cut than a raw image, but
  it is not a drive that lies about its cache, and which writes were lost in
  a given run was not examined.
- **Secure Boot.** Not exercised. `increment` and the expansion under
  lockdown, and whether shim rejects a damaged kernel so that GRUB falls
  back, are open.
- **Refusing an update where attempts cannot be counted**
  (`TUR-BOOT-TRIAL-002`, `ostree admin lock-finalization`): unit-tested only.
- **Counting in userspace when GRUB cannot save** (`TUR-BOOT-TRIAL-005`):
  unit-tested only.
- **Three power cuts in a row during a fallback**: unit-tested only.
- **The product's 240 s limit for the default target** in a stalled boot:
  the stall scenario uses 40 s in its image, as the design allows for pull
  requests. The nightly run with 240 s does not exist.
- **Every moment of a finalisation.** Seven cut points from 0 to 2.8 s after
  systemd announced the stop of OSTree's finalisation, in two runs. Every
  one landed before OSTree changed the boot order: the previous version came
  back whole each time. A cut after the change and before the restart was
  not hit; that window is a fraction of a second.
- **A user's session.** As in TUR-003, nobody logged in.
- **Repeatability.** Each scenario ran in two complete runs (43207801019 and
  43214598212), the second with the program as it is now, on hosted runners. How
  often a scenario fails for reasons of the harness is not measured; two
  such failures were seen and corrected (see "Scenarios").
- `tur-diag collect` on the final system: NOT RUN, the collectors do not
  exist.
