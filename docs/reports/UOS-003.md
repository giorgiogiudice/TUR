## How the disk is produced

`bootc install to-disk --generic-image --via-loopback`, run from the image itself
in a privileged container, writing to a 20 GiB sparse file:

```sh
sudo podman run --rm --privileged --pid=host --ipc=host \
  --security-opt label=type:unconfined_t \
  -v /dev:/dev -v /var/lib/containers:/var/lib/containers -v "$WORK:/output" \
  localhost/uos-boot-test:ci \
  bootc install to-disk --generic-image --via-loopback --filesystem ext4 \
    --karg console=tty0 --karg console=ttyS0,115200n8 --karg uos.boot_test=1 \
    /output/disk.raw
```

This is the invocation bootc documents for its version 1.17.1 (the version in the
image), checked against the documentation at that tag, not from memory.

Why this and not `bootc-image-builder`: it needs nothing that is not already in
the image, so there is no second tool to pin and trust; it is the path the UOS
installer will build on (`bootc install to-filesystem` is the lower half of the
same code); and it worked on the first attempt on the hosted runner, whose
podman (4.9.3) is much older than the one in the image. bootc describes
`to-disk` as an opinionated default rather than an installer, which is what a
boot test wants.

Kernel arguments are added with `--karg`, the documented way to set them at
install time. They become machine-local state in the boot loader entry.

The image sets no default root filesystem (`/usr/lib/bootc/install` is empty),
so the installer refuses to run without `--filesystem`. The test passes `ext4`.
That is a test parameter (`UOS_BOOT_ROOT_FS`), not a decision.

## What the test does

1. Builds the image as the `image` workflow does.
2. Builds `localhost/uos-boot-test:ci` `FROM localhost/uos:ci` with one systemd
   unit and one script (`tests/boot/guest`). **The product image has no test
   hooks.** The agent runs only in a virtual machine whose kernel command line
   has `uos.boot_test`.
3. Installs that image to the disk, then reads the disk from the host through a
   read-only loop device: partition table, EFI system partition content, boot
   loader entries, GRUB configuration. The layout and bootloader are therefore
   measured without relying on the guest.
4. Boots the disk in QEMU 8.2.2: `q35`, `accel=kvm` with no fallback, `-cpu
   host`, 2 vCPUs, 4 GiB, OVMF, virtio disk, user-mode network, `virtio-vga`
   with no 3D, no host display.
5. The serial console is captured from the first firmware line. The agent in the
   guest observes the boot with bounded waits, records facts as files, sends
   them to the host over a virtio-serial port and prints markers on the serial
   console. The host waits for the markers under a 900 s hard timeout, takes
   screenshots through QMP `screendump`, and powers the guest off through ACPI.
6. The agent decides nothing. `tests/boot/report.py` on the host turns the facts
   into checks. A check that cannot be evaluated is "not run" and fails the test
   if it is required.
7. After the virtual machine stops, whatever happened, the persistent journal is
   copied off the disk as a second source of evidence.

The disk is booted twice. The first boot is the disk exactly as installed. The
agent then creates a user and `/etc/plasma-setup-done`, standing in for a person
who completed first-run setup, and reboots. The second boot shows what such a
person would see.

## Answers to the open questions

### Does the hosted runner give working KVM? (ADR-0002)

Yes. `/dev/kvm` exists, owned by `root:kvm` with mode `0660`. The workflow applies
the udev rule GitHub documents for this
(`KERNEL=="kvm", GROUP="kvm", MODE="0666", OPTIONS+="static_node=kvm"`), after
which the runner user opens it and the kernel reports KVM API version 12. QEMU is started
with KVM as its only accelerator, reports `query-kvm` enabled, and the guest
reports `systemd-detect-virt` = `kvm`. Seen on both kinds of runner that turned
up: AMD EPYC (7763 and 9V74, `svm`) and Intel Xeon Platinum 8573C (`vmx`). The
runner had 4 vCPUs, 15 GiB of memory and 86 GB of free disk before any cleanup,
so the workflow no longer removes preinstalled toolchains unless space is short.

### Which bootloader, and what partition layout?

**GRUB 2.12 loaded by shim 16.1, installed by bootupd.** The installer printed
`Bootloader: grub` and `Installing bootloader via bootupd` with nothing passed
to choose one. The firmware console shows `GRUB version 2.12` and one menu entry,
`UOS 0.1.0-dev (based on Fedora Linux 45.20261112.0 (Kinoite)) (ostree:0)`. In
the booted system `bootctl` names the loader as `GRUB 2.12`.

The boot test also reads the certificate table of each EFI binary on the disk and
records whether a signature is attached and which organisations its certificates
name (`bootloader.esp_efi_binaries` in the boot report, and an informational
check). That is presence, not verification: no firmware has checked a signature.

The first boot goes through the removable-media path, which is shim; shim's
fallback then creates a firmware entry "Fedora" for `\EFI\fedora\shimx64.efi`
and puts it first. The second boot went through that entry (`BootCurrent: 0007`).

Layout as installed (GPT, 20 GiB disk):

| # | Name | Type | Size | Filesystem |
|---|---|---|---|---|
| 1 | BIOS-BOOT | BIOS boot | 1 MiB | none |
| 2 | EFI-SYSTEM | EFI System | 512 MiB | FAT |
| 3 | root | Linux root (x86-64) | rest | ext4, created with `-O verity` |

There is no separate `/boot`: the kernel, initramfs and loader entries are on the
root filesystem. The BIOS boot partition and GRUB's BIOS modules are there
because `--via-loopback` implies `--generic-image`, which installs every
bootloader type. 7.0 GiB of the root filesystem is used.

At run time `/` is a read-only composefs overlay, the physical root is mounted
read-only at `/sysroot`, and `/etc` and `/var` are writable parts of the same
partition. `bootc status` reports a `bootcHost` booted from
`localhost/uos-boot-test:ci`, store `ostreeContainer`, no rollback deployment.

**Boot health and automatic rollback: what this stack offers.** Researched, not
implemented (that is UOS-005).

| Mechanism | What it does | Present here |
|---|---|---|
| systemd-boot boot counting and systemd's boot assessment | Counts attempts in the entry file name; falls back when they run out | No. The loader is GRUB; `bootctl` lists "Boot counting" as not supported. bootc supports systemd-boot only with its composefs backend, and this image is deployed with the OSTree backend |
| OSTree's `ostree-finalize-staged` and `ostree-boot-complete` | Detects an update that failed to be finalised at shutdown | Yes, but it does not detect a deployment that boots badly |
| `bootc rollback` | Swaps the boot order to the previous deployment | Yes, when something calls it. Nothing calls it automatically |
| GRUB environment block | A place a boot counter can live; GRUB can read and write it | The block exists and is empty. The GRUB configuration bootupd installs has no counter logic |
| greenboot (Fedora package; from 0.16 a Rust implementation for bootc systems) | Health checks before `boot-complete.target`; a GRUB snippet, installed through bootupd, that counts attempts in the environment block and falls back; performs the rollback | Not in the Kinoite base. It is the existing mechanism to evaluate first |

The specification's assumption of systemd-boot boot counting (§5.3) does not
hold for this base. [ADR-0006](../adr/0006-bootloader.md) proposes the decision.

### How long does boot to the graphical target take?

Measured from kernel start to `graphical.target` active, on the guest's own
clock. Firmware and bootloader time are not included: systemd was not given them.

| | First boot | Second boot |
|---|---|---|
| Run 43153380759 (AMD EPYC 7763) | 25.5 s | 13.0 s |
| Run 43152105040 (Intel Xeon 8573C) | 22.3 s | 10.0 s |
| kernel / initrd / userspace, first run above | 1.4 / 2.8 / 21.3 s | 1.3 / 2.7 / 9.1 s |
| Display manager started | 14.8 s | 11.9 s |

The first boot is slower because of work done once:
`fedora-atomic-desktop-mandb-update.service` alone takes 10 to 12 s and
`graphical.target` waits for it. From the outside, the host saw the first kernel
line 8 s after QEMU started, and both boots, the reboot between them and the
shutdown fit in 127 s.

### Which units fail at boot?

- On an Intel runner: none. The system state is `running` on both boots.
- On AMD runners: `mcelog.service`, on both boots, leaving the system state
  `degraded`. The message is `AMD Processor family 25: mcelog does not support
  this processor`. **This is not an effect of the virtual machine.** The guest
  sees the runner's CPU, and mcelog would exit the same way on AMD hardware.

`mcelog.service` is listed in `tests/boot/expected-failed-units.txt` with that
reason. Any other failed unit fails the test. See "Open items".

### Does Plasma Login Manager start under software rendering?

Yes. `plasmalogin.service` is active on both boots with no restarts, and
`display-manager.service` resolves to it.

- **First boot.** There is no user account, so it does not show a greeter.
  `plasma-setup.service` runs before it and sets up an automatic login; Plasma
  Login Manager logs the system user `plasma-setup` in to a Wayland session
  (logind class `user`, service `plasmalogin-autologin`) running KWin and the
  first-run wizard.
- **Second boot.** With first-run setup marked complete it starts its greeter:
  a Wayland session of class `greeter` for user `plasmalogin`, running
  `kwin_wayland`, `plasma-login-greeter` and `plasma-login-wallpaper`.

On both boots KWin itself reports `Compositing Type: OpenGL ES`, renderer
`llvmpipe (LLVM 23.1.2, 256 bits)`, Mesa 26.2.6. The same session and the same
compositor process are still there after a 15 s hold.

This shows the sessions start without a GPU. It says nothing about GPU drivers,
performance or real displays.

## What the screenshots show

I looked at each of them.

- **First boot** (`screenshot-first-boot.png`, 1280×800): the first-run setup
  wizard. Fedora's default wallpaper of brass gears, the text "Welcome to Plasma
  Desktop", a "Begin Setup" button, "Powered by Fedora Linux" at the bottom, and
  "Restart" and "Shut Down" buttons. Not a login screen, not black, not a
  console.
- **Second boot** (`screenshot-second-boot.png`): the login greeter at rest. The
  same wallpaper, a large clock ("4:22 AM"), the date, and "Show On-Screen
  Keyboard" in the corner. No login form is visible in this state.
- **Second boot after input** (`screenshot-second-boot-after-input.png`): the
  host pressed Shift and moved the pointer. The wallpaper blurs and the login
  form appears: an avatar, the name "UOS boot test" (the user the agent
  created), a password field, and "Sleep", "Restart", "Shut Down" and "Other…".
  99 % of sampled pixels changed, so the display is live.

The automatic screenshot check is deliberately coarse: at least a quarter of the
pixels lit and at least 64 distinct colours. It tells a rendered screen from a
black one or a text console. It cannot tell a greeter from any other picture;
the session checks do that.

## Network and storage

- Network: `enp0s2` gets `10.0.2.15/24` from QEMU's user-mode network, there is
  a default route, the gateway `10.0.2.2` answers ping, and NetworkManager
  reports `connected:full`. A DNS lookup succeeded; the test does not depend on
  it.
- Storage: the virtio disk appears as `vda` with the three partitions above;
  `vda3` is mounted at `/sysroot`, `/etc`, `/var` and `/boot`. A 3.8 GiB zram
  swap device is active. Memory in use after the greeter is up: 1.6 GiB of 3.9.

## What is not proven

- That UOS boots on any real machine, with any real GPU, firmware or disk.
- Secure Boot. `bootctl` reports `disabled (unsupported)`; the OVMF build used
  has no Secure Boot. Fedora's shim and GRUB are on the disk; nothing has
  verified their signatures.
- A user logging in and reaching a Plasma desktop. The sessions seen are the
  first-run wizard's and the greeter's.
- That the first-run wizard works. It was displayed, not operated.
- BIOS boot, although the disk carries it.
- Anything about updates, rollback or recovery.
- Boot with disk encryption, or on a filesystem other than ext4.
- That installing from a host with SELinux gives the same labels. The install
  ran on Ubuntu, which has none; bootc records this as "host-disabled".
- Repeatability beyond three runs on two kinds of runner.

## Open items

Things this task found and did not change, because each is its own decision.

1. **`mcelog.service` fails on AMD CPUs and leaves the system `degraded`.** It
   is enabled in the base. AMD is the first-choice validation hardware (§4.1),
   and a health gate that looks at failed units (§5.4) would see it on every
   boot. The image should stop it failing on AMD, for example by disabling it
   or by a condition on the CPU vendor. Until then it is listed as expected in
   the boot test, which hides nothing but does let it pass.
2. **The image has no default root filesystem.** `bootc install to-disk` fails
   without `--filesystem`. The installer (UOS-006) must choose. bootc treats
   ext4 and btrfs as supporting fs-verity, which composefs wants, and xfs as
   not supporting it.
3. **Fedora's name appears where UOS's must** before any image is published:
   "Powered by Fedora Linux" in the first-run wizard, the firmware boot entry
   "Fedora", the ESP directory `EFI/fedora`, and the host name `fedora`. The
   last three come from Fedora's signed shim and GRUB packages (ADR-0006).
4. **First boot is a setup wizard, not a login screen.** Whoever designs the
   installer needs to know that account creation currently happens here, in
   KDE's `plasma-setup`, after installation.
5. **SELinux denials in the journal**, 13 on the first boot and 9 on the second,
   none of which stops anything: `bootupctl` reading `/sysroot/.bootc-aleph.json`
   (labelled `default_t`; the bootupd domain is permissive), and bootc probing
   its own privileges with a deliberately invalid label each time
   `bootc status` runs. Worth knowing before UOS-004 treats denials as errors.
6. **The boot report has no schema.** `boot-report.json` carries
   `schema_version: 1`; a schema under `schemas/` should follow once its shape
   has settled, as the build manifest has.

## Corrections to earlier assumptions

- Specification §5.3 assumes systemd-boot boot counting. The base uses GRUB.
- Specification §27.1, stage BOOT-110, speaks of a display manager's login. On
  first boot the display manager's session is the setup wizard; the health gate
  must accept either.
- UOS-002 recorded "GRUB 2.12 and shim 16.1; no systemd-boot" from the package
  list. That is now confirmed from an installed and booted disk.
- The `image` workflow frees disk space on every run. On the runner seen here
  86 GB were free beforehand and the build needs about 15 GB.
