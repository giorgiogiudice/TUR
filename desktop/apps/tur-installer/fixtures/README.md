# Recorded answers of the installation engine

The graphical installer is built, tested and photographed where no engine can
run: the engine needs root, real disks and the installer medium. With
`--fixture DIR` (or `Engine.fixture`) every step replays `DIR/<step>.jsonl`,
one JSON object per line, in the format
`installer/iso/rootfs/usr/libexec/tur-installer/tur-install-engine` writes.
A first line without an `"event"` key carries the licence and says what the
file is. `{"event":"pause"}` stops a replay where it is, without an end, for
the states in the middle of an installation.

| Directory | What it is |
|---|---|
| `beside-windows/` | The virtual machine of `tests/iso`: the medium as a USB stick, a blank 20 GiB disk, and the Windows-like disk of `tests/iso/make-windows-disk.sh`. Installations that succeed, fail while copying, are refused because the disk changed, and are held while copying or before writing |
| `same-disk/` | The virtual machine of the iso workflow's `beside` job (ADR-0028): the medium, a disk laid out by `tests/iso/make-windows-shared-disk.sh` (Windows after Shrink Volume, 24 GiB free: TUR can go beside Windows) and the same layout with no free space. Installations beside Windows that succeed, are held while copying, and fail while copying |
| `blocked/` | The checks of a computer with too little memory, started from a damaged medium |
| `no-disk/` | The medium and one disk that is too small |

**Written by hand**, in the engine's format, with the disks of the virtual
machine and bootc's lines from iso run 43291029560. Unlike the application
centre's fixtures, they are not regenerated by CI: the engine cannot run in
the desktop workflow. The engine logs every line it sends ("ENGINE> " in
`installer.log`, which is kept on the installed disk), so the `iso` workflow's
installations are where to compare them with the real thing.
